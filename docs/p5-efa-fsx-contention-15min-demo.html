The narrow question

When both paths run together, which one absorbs it?

A distributed trainer can be reducing gradients while an asynchronous checkpoint writer drains tensors to shared storage. Asynchronous checkpointing can reduce trainer blocking, but the bytes still cross the same NICs. So: hold the fleet, the filesystem, the duration and the payloads constant, and change only whether the two workloads overlap.

Held constantValidated value
Compute2 × Spot p5.48xlarge, one exclusive Slurm allocation
GPUs8 × H100 80 GiB per worker · 16 total
EFA32 devices per worker
NCCL world16 ranks, 8 per worker · 256 MiB float tensor per rank
FilesystemDedicated EFA-enabled Lustre Persistent 2 SSD at /fsx-efa
Capacity19,200 GiB at 1,000 MB/s/TiB
Arm duration90 seconds, both workloads

The dedicated filesystem is separate from the shared /fsx mount, so the experiment never touches production model or training data.

Both workloads start from one shared future UTC epoch. Overlap is engineered, not hoped for — the arms would otherwise measure two staggered workloads.

What this is not. The writer is a checkpoint-like data-plane workload. It has no PyTorch serialization, no optimizer-state assembly, and no Distributed Checkpoint metadata. It reproduces the byte movement, not the full checkpoint stack.

Spot caveat, stated by the lab: a Spot interruption invalidates an arm. The partial evidence is preserved, the measurement is discarded, and the arm is rerun under a new label.

The isolated arms are what make the signatures readable. EFA hardware counters remain NIC-aggregate: they do not tag bytes by PID, container, NCCL communicator, or cuFile handle. That is enough for controlled correlation in this experiment, and it is not per-process accounting.

The operational read is narrow and useful: asynchronous checkpointing reduces trainer blocking, but it does not make storage traffic free. Before this becomes a production policy, the lab asks for five things.

  • 01Repeat each arm several times and report confidence intervals
  • 02Replace the synthetic writer with the application's real checkpoint stack
  • 03Sweep checkpoint concurrency and file stripe settings
  • 04Correlate step-time, NCCL, cuFile, Lustre and EFA metrics on one timeline
  • 05Revalidate after any change to AMI, kernel, driver, CUDA, GDS or FSx type

One controlled synthetic 90-second run per arm on one two-node Spot allocation. Repeat the experiment before turning these values into policy.

Appendix C

Each workload left a different fingerprint

EFA counters were delta-sampled before and after each measurement window. Because the isolated arms ran alone, their signatures are distinct in this controlled run — and the overlap arm's containing both is what confirms the two paths were genuinely concurrent.

ArmDominant EFA counterVolume over the windowWhat it proves
A · NCCL only rdma_write_bytes ≈ 30 TB Collectives push payload outbound over SRD
B · Checkpoint only rdma_read_resp_bytes ≈ 639 GB The filesystem pulls from GPU memory; the writer is the target, not the sender
C · Overlap both both present The two paths were concurrent on the same NICs, in the same window

What the counters do prove: the intended transport carried the traffic, in the exact window, with zero RDMA write errors and zero receive drops.

What they cannot prove: which process, container, NCCL communicator or cuFile handle produced any given byte. Counters are per NIC and port.

The two volumes are not comparable as a ratio — they count different operations on different sides of the transfer. The direction of each signature is the evidence, not its magnitude.
